# 2026-10-07：执行证据与可重复验收

本轮完成了指令调整和四次 Windows Claude Code 成对试验，但候选版没有通过全部功能验收，不能推荐为已证明更好的升级。保留失败产物和可复跑检查；该轮评测期间没有修改全局安装或发布新版本。

## 指令改动

- 将影响选型的事实关联到实际查阅的材料、定位信息和本地影响；搜索摘要、未读链接和抓取失败不能充当已核实的排除理由。
- 区分具体命令失败与整个运行环境不可用，限定恢复动作的权限和范围。
- 把验收压缩为“重要承诺 → 能推翻它的输入或状态 → 预期最终结果 → 实际结果”。检查提交后的状态，不能用取消操作或自测数量代替。

入口从 1,920 个空白分词缩至 1,828 个；新增按需读取的 [execution-evidence.md](../../references/execution-evidence.md) 为 603 个。总材料没有变少，也不能用长度衡量效果。没有更改自动触发描述、增加运行依赖或要求普通任务生成完整台账。这种条件加载方式参考 [Agent Skills 编写指南](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)。

## 来源、范围与评审限制

功能通过与研究依据充分是两个结论。搜索 A 将只见于搜索摘要的 Algolia 和二手文章列入“一手证据”；B 确实读到了更多原始摘录，但把 AbortController 已列出的用途说成排他的“只能”，又把当前 API 没有取消接口扩写为定时器无法取消。这些说法超出了证据。

联系人两边提到 Google Contacts 的流程，却都只有搜索摘要；本地导入实现可用，不能补成“已经调查了外部产品流程”。A 实查了 PapaParse 的包元数据和发布文件，但最终体积比例有夸大。B 确实执行了与 PapaParse 的对照；它又声称同样对照了 d3-dsv，但已执行脚本和结果里没有对应代码或输出。B 自报的 35 项通过有执行记录，却没有覆盖本轮失败的输入。

WebFetch 的域名安全检查失败后，部分试次转用 Node/Python 获取页面。后续摘录能证明读到了哪些内容，不能消除先前的访问边界问题，也不能把另一条路线成功当作已经获准。新增指南中的权限提醒没有稳定约束所有行为。

候选版两题还在任务目录外创建了三份 Claude 项目记忆文件。协调器通过成功的 Write 结果、正文和会话标识核实归属，备份完整字节并校验 SHA 后只删除这三份试验文件。这个范围违规保留在记录中；清理不将其改记为“未发生”。没有更改其他用户记忆。没有发现试验结束后遗留的相关 HTTP 服务。

A 的导入试次也将测试脚本写入了系统 Temp 下的试验目录，当前还有 CSV 和截图共 16 个文件。已另存副本并核对哈希；由于没有该共享临时目录的运行前清单，保留原目录，没有假定其中全部内容可删除。协议中的外部记忆写入计数不代表所有目录外文件写入的总数。

每题每条件只有一次，无“完全不用 skill”条件，不能推断稳定提升。联系人评审在筛选日志时意外读到了 skill 内容，因此不称完全盲评；功能检查仍遵循冻结标准。搜索评审没有读取技能正文或版本映射。主观来源判断不作为严格因果证据。

搜索脚本的负对照是未修改的原始夹具：能检测到旧结果覆盖和失败恢复表达问题并返回 1；A、B 修复产物返回 0。导入脚本在 A 上返回 0，在 B 上返回 1，且默认 CRLF 文件哈希与冻结失败输入一致。搜索脚本还验证了 API 子项失败会进入总判定、浏览器不可用不会计为通过、已有输出不会被覆盖。这些是浏览器与维护工具复核，没有增加实现模型试次。

原始宿主事件、浏览器截图及越界写入备份留在本机评测目录，不随公开仓库分发。公开协议只保留必要元数据和清理事实。
