# Project Identity Card

> Optional reusable context for a longer project. Fill from evidence, mark unknowns,
> and update when requirements or external state change. It does not replace
> feature-specific research or the user's current instructions.

---

**Project Name**: [name]

**What problem does it solve?** (one sentence — the WHY, not the WHAT)
[This project is a ____ that helps ____ solve ____ by ____.]

**Who uses it? At what scale?**
- Primary users: [developers? data analysts? enterprise teams?]
- Scale: [single-user? team? enterprise? public SaaS?]
- Context: [internal tool? customer-facing? open source?]

**Hard constraints** (the non-negotiables)
- Security: [auth required? data sensitivity? compliance (SOC2/GDPR)?]
- Performance: [latency SLA? throughput? resource limits?]
- Accuracy: [numerical precision? no hallucinations? audit trail?]
- Cost: [budget constraints? free tier? per-user pricing?]

**What makes it different?** (vs alternatives)
- [Key differentiator 1]
- [Key differentiator 2]

**Tech DNA** (stack + why they chose it)
- Language/Framework: [Python/FastAPI — because ____]
- Database: [SQLite — because ____]
- Key dependencies: [list 3-5]
- Code conventions: [naming, error handling, test patterns]

**Pain points** (what keeps the maintainer up at night)
- [Hardest part of the system]
- [Most common failure mode]
- [Technical debt that's accumulating]

**Research implications** (how identity shapes search)
- Relevant search context: [project type, domain, stack, audience, target version]
- Existing reusable resources: [installed libraries, design system, templates]
- Prior-art questions: [similar products, open-source implementations, better techniques]
- Preferred reference types: [primary docs, source/tests, product examples, datasets]
- Last checked: [date and source revisions; assumptions requiring recheck]
