# From Evidence to Executed Acceptance

Use the access procedure when source retrieval or a required execution route is
uncertain. Use the acceptance procedure for changed state, compatibility or
recovery promises. Keep the record in the decision summary or existing ledger;
this guide does not require another document or extra checks for mechanical edits.

## Resolve the Actual Access Failure

Try a harmless representative operation when the plan depends on an unfamiliar
tool or uncertain capability. Record the tool, operation, result and what that
result establishes. Tool listings show availability, not a successful invocation.

- **Command composition or tool mismatch:** a refused compound command does not
  prove its runtime is absent. If a smaller operation is already permitted, run it
  on its own in the intended working directory. Do not wrap a denied action in a
  different interpreter or use another route to evade a permission or path boundary.
- **Missing executable, dependency or connection:** separate this from application
  failure. Use an existing permitted alternative when it answers the same question.
  Do not modify global configuration or add services outside the user's scope.
- **Unread source:** distinguish a transport/format failure from an access denial.
  Use another authorized source or local copy for the claim, without bypassing a
  restriction. Search summaries remain leads; record exactly what was inspected.

Retry only when the next attempt tests a materially different, permitted cause.
Repeated denial is a limit to record, not a reason to probe more routes. Continue
contained authorized work and narrow its claims; defer only dependent actions
whose missing evidence or authority matters.

## Turn a Contract Into a Counterexample

Before implementing, connect each important promise to an observable result and
a case that would falsify it. Derive cases from the request, actual input contract,
chosen reusable component and local integration boundary, not just existing tests.
For example, a response can contain usable data and diagnostics simultaneously;
inspect its acceptance policy before treating a returned value as successful work.

State the relevant support boundary: accepted structure or states, applicable
versions/environment, and what rejection or recovery preserves. Exercise a case
across that boundary when the promise depends on it. If compatibility is based on
structure rather than a version field, explain and check that policy. Partial
success can be valid when the contract permits it; disclose what was applied,
skipped and preserved rather than silently choosing a loss policy.

## Observe the Promised Outcome

Execute the chosen counterexample through the entry point the user will use and
observe the completed result, including failures. Distinguish these checks:

| Promise | Evidence needed |
|---|---|
| Rejected work preserves data | Submit the invalid operation; inspect final data and feedback. Cancellation tests a different path. |
| Changes survive a return | Complete the change, leave/reload/reopen as relevant, and inspect restored values. |
| Recovery restores usable interaction | Trigger the failure, attempt the supported next action, and inspect state and focus/feedback where relevant. |
| An exported artifact is usable | Inspect the produced artifact and exercise the relevant consumer or round-trip boundary. |
| A guide works on a named platform | Carry that platform's commands through first success and relevant recovery. |

Choose applicable rows only. Library tests or DOM substitutes establish their
tested boundary; they do not establish the assembled browser, service or reader
journey. If the boundary cannot be exercised, keep acceptance unverified even when
static inspection looks correct. Record the actual reason, not an unattempted
tool's supposed failure. Preserve the concrete failed case, fix within authorized
scope and rerun it; update the record rather than replacing failure with a test total.
