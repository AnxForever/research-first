# WorkBuddy 发布包

本包依据 [WorkBuddy 官方技能文档](https://open.workbuddy.cn/docs/skill)制作。
`1.0.0` 是独立 WorkBuddy 包的首个版本号，作者沿用仓库版权署名 `AnxForever`。
它不代表原仓库已经使用同一版本体系。

## 生成与本地校验

在仓库根目录执行：

```bash
python -m pip install -r scripts/requirements-dev.txt
python scripts/build_workbuddy.py
```

输出为 `dist/workbuddy/research-first-workbuddy-1.0.0.zip` 和同名 `.manifest.json`。
在开放平台选择上传 **ZIP 文件**；manifest 留作本地版本核对，不放入技能包。
旧的 `dist/research-first-*.zip` 是历史产物，不应用作本次上传包。

构建从当前 `SKILL.md`、`references/` 和模板读取内容，元数据来自
[workbuddy.yaml](workbuddy.yaml)。构建会校验暂存目录，生成 ZIP，再解包校验。
manifest 记录源码提交、工作树是否有未提交改动、输入和归档文件的 SHA-256。
同一构建环境中的相同输入生成相同 ZIP；同版本重新构建会更新该版本产物，最终上传前核对 manifest。

生成包的结构如下：

```text
research-first/
├── SKILL.md
├── LICENSE
├── references/          # 按需读取的指导、案例和 Jev 证据卡示例
├── templates/           # 调研报告模板和项目背景卡
└── scripts/             # 仅可选 Jev 预览/复核需要
```

WorkBuddy 包使用 `@references/...` 与 `@templates/...` 引用资源。
其中 `@references/...` 来自官方文档；`@templates/...` 是本包采用的根目录相对路径约定，仍需在宿主内验证读取。
构建将原仓库的 `assets/` 映射为 `templates/`，并同步修改交叉引用。
原仓库的 `SKILL.md` 和引用路径继续作为其他宿主的单一来源。
历史评测保留为指向 GitHub 提交的链接，不随包携带完整评测夹具、测试代码或原始日志。

核心流程只需 Markdown 指令，以及 WorkBuddy 提供的搜索、文件读取和执行工具。
若平台提供文档检索工具，应优先按项目版本查询；缺少该工具时按技能内的回落规则处理。
Jev 为可选功能；包内的 Python 脚本默认只预览请求，无需 SDK 或 API Key。
用户明确启用真实复核时，才需要安装可选 SDK、配置密钥并使用 `--live`；
该请求会把用户明确提供的证据卡发送给 TypeSafe。脚本须从实际安装的技能目录运行。

## 刊登介绍

**名称：** Research First｜先调研再实现

**简短介绍：** 先理解目的，调查现有方案与一手资料，呈现选项和取舍，再按任务分量实施与验证。

**详细介绍：**

用户提出一个想法后，Research First 指导 AI 先查看项目现状，厘清目的与约束，
调查现有产品、可复用方案和权威资料，再说明采用、改造、组合或自研的理由。
调研完成后，AI 在已授权的范围内继续实施，并通过关键反例检查实际结果。
如果你只要求调研或审阅，它会停在分析和建议。

适合新功能、交互设计、技术选型、系统集成，以及需要比较方案的重要文档工作。
当你质疑现有方案时，它会重新检查可能推翻原判断的证据。
普通事实问答和不改变行为的精确修改无需启动完整流程。

小任务保留简短的证据、选择与检查记录；多功能、跨会话或高风险任务使用逐功能证据台账。
实际效果取决于当前模型和工具能力。它不保证总能找到可直接采用的方案，
现有评测也不足以证明跨模型、跨任务的普遍提效。核心使用不需要注册第三方 API。

**示例提示词：**

1. 给现有管理台增加可筛选、可排序的数据表。先查看项目已有组件，调查合适方案和官方资料，简短说明选型取舍，再实现并检查空态和关键交互。
2. 我想把当前表格换成专用表格库。只做调研，不改代码；比较保留现有组件和可信候选，说明兼容性、许可、接入成本、推荐和待验证项。
3. 给搜索页增加日期范围筛选，必须沿用当前框架且不新增依赖。先检查现有模式和接口契约，再实现并验证日期边界、空值和重置行为。

## WorkBuddy 内待执行的验收

本地结构校验不等于平台解析、自动触发或模型执行成功。
以下项目必须在 WorkBuddy 内实际运行后才能标为通过；当前均为 **未验证**。

| 检查 | 操作和通过条件 |
|---|---|
| 导入与展示 | 导入新 ZIP，核对技能名、中文/英文简介和版本，没有解析错误 |
| 显式调用 | 在对话中选择已安装技能，提出上面的只调研示例；应呈现证据和选项，不修改文件 |
| 自动触发 | 新会话中提出有选型需求的任务，不手动指定技能；查看宿主是否实际加载此技能，不能只凭回答风格判断 |
| 简单任务边界 | 新会话中询问 HTTP 404 的含义，或在测试项目只改按钮文案；不强行进行产品比较或扩大任务 |
| 参考文件读取 | 提出需要比较两个实现方案的任务，检查实际工具记录能否读取 `references/reuse-and-alternatives.md`，且没有一次加载全部参考资料 |
| 模板使用 | 明确要求生成一份调研报告，检查对应模板可读取，输出中的结论和来源来自当前任务 |
| 约束和降级 | 在禁止新增依赖、无法联网的测试项目中完成可逆任务；保持约束、说明证据缺口，不编造已经读过的资料 |
| 执行与验收 | 在隔离测试项目实现一个功能，检查是否执行关键反例并核对最终结果，分别报告通过和未验证项 |
| 可选脚本 | 用户主动启用 Jev 预览，在技能安装目录执行 `python scripts/jev_check.py --help`，再预览一张证据卡；不加 `--live`，应成功且不请求外部 API |

记录宿主版本、模型配置、包 SHA-256、输入、实际工具记录和结果。
测试项目使用合成数据，不对真实业务数据做坏输入实验。
开放平台审核与公开发布另按平台流程完成，本地构建不会自动上传。
